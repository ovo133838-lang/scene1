# scene1-business-check

版本0.2，2026-11-12，AI协助编写；学生作者/审核和学生指导纠错仍须真实记录。0.1内容见历史调用产物，不能以本次更新补造开发前历史。

用途：检查题1跨订单、库存、收款、退款、发货约束，适用于开发自检、独立测试和缺陷复测。触发场景：业务实现/迁移/接口修改后，或出现重复通知、迟到支付、库存不守恒、退款结果冲突、崩溃恢复问题时。仅用于题1教学隔离环境。

输入：原始共通要求+题1、U01–U06、当前AGENTS/契约、源码基准及工作区哈希、隔离MySQL及独立模拟渠道地址、允许测试的库名、已有失败原件。凭证从环境读取，不写输出。

执行步骤：

1. 从`apps/scene1/internal/repository/schema.json`、`migrations/*.sql`、运行库information_schema提取实际表列；从`internal/httpapi/api.go`和`cmd/scene1/main.go`提取实际路由，区别业务字段、生成列、技术表和静态fallback。契约差异先列出，不用旧256/48数字替代清点。
2. 沿创建→占用→取消/到期关闭或有效付款→退款申请/审核或发货→退款确认核对逐步持久化结果。正常售前退款只释放一次，关闭后迟到款退款不释放；未知退款继续冻结并查原键，明确失败才新attempt。
3. 实际执行20不同请求同步争5件、退款申请vs发货、同键重复/异参、交易号冲突、满10分钟、他人资源和角色越权。记录请求键、状态、DB前后与库存/资金守恒。
4. 对真实列和路由逐项验证适用约束；字段元数据核对、路由被调用都不能冒充完整行为通过。直接SQL反例和服务层不可变性分开记录；签名失败仍须保留可查异常，非法写入须回滚。
5. 用隔离HTTP代理/数据库故障夹具验证渠道成功响应丢失、事务写失败、提交成功响应丢失、worker调用前后崩溃与租约恢复。不在生产加入可公开触发的故障开关，不持写锁等待外部HTTP。

输出格式：每项记录`case_id / rule或真实table.column或method path / 目标哈希 / 输入动作 / 预期 / 实际HTTP与DB前后 / PASS|FAIL|BLOCKED|NOT_RUN / 原件路径`。汇总实收-实退=净额、初始+调整=可售+占用+出库，并列未测维度与原因。

失败处理：保留首败和最小复现，独立测试只修改测试/夹具，生产缺陷交开发；开发修复后锁定新哈希，复跑原例及受影响场景。测试预期错误须依据原题/真实契约解释修正，不能隐去失败或降低业务门槛。依赖缺失写BLOCKED，不编造输出。

完成标准：声明范围内每项均有可重复原件、无未处理业务失败且守恒成立；未测项明确列出。Skill检查通过不代表独立验收、学生审核、Git或部署完成。
