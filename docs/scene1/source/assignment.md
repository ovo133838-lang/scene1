# Go 项目业务场景题

适用水平：约 3 年 Go 后端开发经验。共 20 题，每题独立，个人完成，每题限时 1 天，按 8 小时安排。每人每天至少完成 1 道题，并在当天完成班级群讲解及效果视频提交；仅代码写完不计完成。

本题集只包含题目、开发要求与验收要求，不提供答案、实现方案、代码或 Skill 成品。

每题均要求还原一个有多方参与、多个业务分支和结果核查的完整工作场景：先理解业务如何发生、不同角色为什么操作以及异常如何收尾，再自行完成需求分析和实现。不得只完成其中一条成功路径或一个技术功能点。

业务来源：用户提供的《Golang岗位-热门城市且薪资_14k.csv》。各题中的公司名称、岗位名称和职责摘录来自该文件，岗位链接供溯源，未另行核验岗位当前有效性。涉及招聘服务商或外包岗位时，公司名称仅代表 CSV 所列招聘主体，不据此认定其为业务系统所有者。业务背景根据职责范围改编；数量、时限、状态、价格及异常规则均为本题教学设定，不代表公司实际内部规则。

## 一、所有题目共同适用的要求

本节是每一道题题面的一部分。单题要求与本节共同构成完整考题，提交时不得遗漏。

### 1. 实现范围与环境

1. 使用 Go 实现核心业务，以本题定义的完整业务闭环为交付范围，不要求搭建完整商业平台，不强制微服务拆分。
2. 必须实现可操作的最小业务页面，用于发起业务、查询结果和展示失败原因；页面可使用简单 HTML，不要求复杂视觉设计。
3. 必须使用数据库保存核心业务数据，服务重启后业务结果仍可查询；数据库类型自行选择并说明。缓存、消息队列等组件按实际需要选用，不以组件数量评分。
4. 允许使用既有项目脚手架、UI 组件和部署模板，但必须说明来源及本题新增内容。不得直接提交现成的完整业务项目。
5. 第三方服务可采用可控的 HTTP 模拟服务，必须能触发题面要求的成功、失败、超时及重复通知场景。不得将模拟服务当作真实第三方接入成果。
6. 教师须在开考前提供或确认可用的 GitHub MCP、仓库创建及分支规则权限、meegle CLI 与指定飞书项目访问权限、真实需求编号、缺陷登记渠道、部署目标、CI 执行环境及必要访问权限；学生可预先准备通用开发环境，但本题业务实现必须在考试期间完成。
7. 本题“上线”指部署到指定教学验收环境，须有可访问的服务地址和真实部署记录。
8. 为控制一天工作量，各题均采用固定的小规模数据、少量角色及简洁页面；账号可预置，外部系统可模拟，通知可采用站内消息。不要求注册登录全套流程、真实短信或复杂后台，但角色身份必须可信，不能通过随意修改请求中的用户编号越权操作。
9. 各题要求的业务分支均须可实际操作并有持久化结果，不能用静态页面、写死成功结果或文档说明代替。时间边界可使用可配置教学时钟或缩短时长演示，必须注明；测试和线上演示须使用相同业务规则。

### 2. 必须完成的开发流程

严格执行：**需求分析 → 原型设计 → 任务规划 → Agent 开发 → Agent 测试 → Agent 验收 → 自动部署上线**。

| 阶段 | 学生必须完成的内容 | 必须保留的证据 |
| --- | --- | --- |
| 需求分析 | 明确角色、主流程、业务规则、边界、异常和可验证的验收条件 | 需求说明、业务流程或状态说明、假设清单 |
| 原型设计 | 制作可点击或可操作的轻量原型，展示主要操作、结果及异常状态 | 原型文件、页面状态说明 |
| 任务规划 | 拆分实现、测试、验收、部署任务，标记依赖及每项完成条件 | 任务清单、任务编号与需求对应关系 |
| Agent 开发 | 使用 AI Agent 完成业务开发，学生审核并修正其产出 | 开发会话、代码版本、审核和修正记录 |
| Agent 测试 | 使用独立测试 Agent 会话制定并执行测试，发现缺陷后交回修复 | 测试会话、实际测试结果、缺陷及复测记录 |
| Agent 验收 | 使用独立验收 Agent 会话，依据原始题面逐项验证最终版本 | 验收会话、逐项结论及证据位置 |
| 自动部署上线 | 由流水线执行质量检查、构建、部署及上线冒烟检查 | 流水线配置与运行记录、部署地址、版本标识、冒烟结果 |

三个 Agent 角色可以使用同一工具、同一模型，但必须使用相互独立的会话或任务上下文。测试与验收角色必须读取原始题面和对应版本代码，不能仅根据开发 Agent 的完成声明判断通过。

建议时间分配：MCP 建仓与 Agent 约束准备 20 分钟、需求分析 35 分钟、原型设计 20 分钟、任务规划 20 分钟、开发 180 分钟、测试 75 分钟、验收 40 分钟、Git 合并与自动部署 35 分钟、Skill 总结与视频录制提交 55 分钟，共 8 小时。各阶段材料保持简短，以可执行和可核查为准。测试或验收发现问题时，须修复后重新验证受影响阶段。

### 3. AI 规则约束

学生必须在业务开发开始前自行编写并实际使用项目级 `AGENTS.md`，不能只复制通用规则或完工后补写。约束须针对本题，至少明确：

- 开发、测试、验收 Agent 的职责、交接材料、可修改范围、需要学生确认的事项，以及不得擅自扩大实现范围的边界。
- 仓库、开发分支、主分支及 PR 操作权限；提交格式、工作项编号核验、合并和部署前置门禁。
- 项目代码约定、业务数据保护要求、单元测试覆盖率要求和失败后的修正复测流程。
- 业务规则以题面为准；未明确事项必须记录假设，不能将猜测当成既定需求。
- 开发前分析业务及验收条件，完成后提交真实执行的验证证据。
- 禁止编造接口、依赖用法、执行结果、测试报告或部署成功记录。
- 禁止通过删除失败测试、弱化断言、跳过关键路径、任意排除生产代码来达到覆盖率要求。
- 禁止泄露密钥和用户敏感信息；日志、截图和对话导出均须脱敏。
- AI 生成代码必须由学生检查；发现错误后应保留问题、修正要求和复测过程。

必须提交约束文件的历史版本、实际加载或读取记录及对应任务，说明哪些行为受到约束、是否调整过约束、为什么调整；不能只在结束时补写文件。

### 4. 自行编写并使用 Skill

每题至少自行编写两个与本题相关的 Skill：

1. **业务专项 Skill**：按单题要求，检查或辅助处理本题的关键业务约束。
2. **验收检查 Skill**：依据题面核对需求实现、异常路径、测试证据和部署结果。

每个 Skill 必须包含：用途、触发场景、输入、执行步骤、输出格式、失败处理及完成标准。必须提交可被所选 AI 工具使用的 Skill 文件、工具中的配置方式，以及实际调用记录。

至少展示一次“Skill 检查发现问题 → 学生指导 Agent 修正 → 重新检查”的实际过程；如未发现问题，应保留检查范围和依据，不得编造缺陷。不得把一句角色设定或通用提示词作为完整 Skill 提交。

完成后必须一并提交 `skill-usage.md`，汇总所有实际使用的 Skill，包括自编、修改和直接使用的既有 Skill。每项须填写以下内容，未实际调用的不得列为已使用：

| 说明项 | 必须回答的问题 |
| --- | --- |
| 名称、来源与版本 | 使用了哪个 Skill？自编、改编还是既有？文件在哪里？ |
| 使用位置 | 在哪一阶段、哪项任务、哪次会话使用？对应记录在哪里？ |
| 使用原因 | 当时遇到什么具体问题，为什么选择这个 Skill？ |
| 使用过程 | 提供了什么输入，实际执行了哪些检查或步骤？ |
| 实际帮助 | 得到什么结果，帮助发现或避免了什么问题，改善了什么？ |
| 证据及局限 | 对应输出、修改和复测在哪里？有哪些无效、误判或需人工补充的地方？ |

使用帮助须结合本题实例说明，不能只写“提高效率”“保证质量”，也不得编造节省时间或发现缺陷的数据。视频中须结合实际过程讲解这些内容。

### 5. 导出全过程提示词及 AI 使用记录

必须导出从需求分析到上线验收的全部可见会话，按阶段保留时间顺序，至少包括：

- 学生输入的全部提示词、补充上下文、纠错要求和可见 AI 回复。
- 学生自行配置的 Agent 指令、`AGENTS.md` 及 Skill 的版本和使用记录。
- 工具调用、命令输出、失败重试，以及涉及的图片、原型和附件索引。
- 每个阶段使用的工具、模型、任务编号和关联代码版本；工具不暴露的模型版本等字段应标为“不可获取”。

同时提交可读的 Markdown 会话导出和按时间排序的结构化事件清单（JSON 或 JSONL）。无法导出的平台内容应列出缺失范围；无需获取平台隐藏指令或模型隐藏推理。

另提交一页 AI 使用说明，列明各阶段 AI 与学生分别完成的工作、学生实际审核的内容，以及有记录依据的纠错情况。AI 使用程度依据过程证据核查，不以提示词数量或自报代码生成比例代替。

### 6. 测试与 AI 产出质量要求

1. 本题自编 Go 生产代码的整体单元测试语句覆盖率必须 **≥85%**，各核心业务包分别 **≥85%**。集成测试覆盖率不得代替单元测试覆盖率。
2. 覆盖正常流程、边界条件、非法状态、重复操作、权限校验及本题指定异常路径；并发要求必须有可重复执行的并发验证。
3. 自动生成文件和第三方代码可排除；自编数据库访问、HTTP 处理等代码不得自行排除。其他排除项须由教师事先明确，并在报告中列出。
4. 提交单元测试命令及原始输出、覆盖率原始文件、可读报告，以及必要的数据库集成测试和接口测试结果。
5. 使用 Go 格式检查、`go vet` 和相关测试；含共享并发访问的逻辑须执行竞争检测。质量检查失败不得继续发布。
6. Agent 验收须检查业务正确性、权限、数据一致性、错误处理、可维护性和敏感信息处理，并对照题面逐项提供证据。
7. 开发分支测试、PR 检查、Agent 验收和合并必须有明确的提交版本对应关系；主分支合并提交若与原测试提交哈希不同，须记录 PR 与源提交关系，并对主分支实际发布提交重新执行流水线门禁。部署制品、上线服务和上线验证必须对应该发布提交。验收后修改业务代码，必须重新运行受影响检查。
8. 教师将独立运行验收用例并审查代码、Skill 和 AI 使用记录。AI 自述“通过”不作为通过依据。

### 7. 自动部署与最终提交

仅允许对经 PR 合并且门禁通过的主分支版本执行正式教学环境发布，开发分支可运行测试或预览部署。必须提交可实际执行的自动部署流水线。流水线至少包含质量检查、单元测试及覆盖率门禁、构建、部署、健康检查和业务冒烟检查。仅提交 Dockerfile 或手工启动截图不算完成自动部署。

必须完成一次实际部署，提交运行地址、流水线运行标识、部署版本及结果，并说明如何恢复到上一可用版本。首次部署应说明失败时如何撤销本次发布。

最终交付清单：

- 需求说明、原型和任务清单。
- 完整源码、运行说明、数据库初始化或变更文件、演示数据和第三方模拟服务。
- 项目 `AGENTS.md` 及版本和生效说明、至少两个自编 Skill、全部实际使用 Skill 的清单、使用记录及 `skill-usage.md`。
- GitHub MCP 创建仓库记录、仓库与开发分支链接、提交历史、工作项核验结果、PR 与合并记录。
- 班级群提交记录、可访问的讲解和效果视频及带时间点的讲解目录。
- 全过程提示词与可见会话导出、结构化事件清单、AI 使用说明。
- 单元测试与覆盖率报告、接口或集成测试结果、缺陷及复测记录。
- Agent 验收报告、CI/CD 配置、实际部署记录、服务地址和上线冒烟结果。

关键业务验收不通过、覆盖率未达标、缺失自编 Skill 或使用记录、AI 过程无法追溯、自动部署未成功、Git 流程不合规、缺少每日群提交或视频未讲清要求，均不得判定整题通过。

### 8. GitHub 仓库、开发分支与合并流程

本节是教师新增的流程要求。第 9 节的提交消息、工作项编号及校验要求来自提供的 `commit-convention.md`；该文件没有定义分支命名或 PR 策略，不得将本节新增规则误称为原规范内容。

1. **开发前创建仓库**：每人每题通过 GitHub MCP 创建独立仓库，保留工具名称、请求与结果、时间、仓库 URL。不得用手工创建、CLI 创建记录替代 MCP 创建证据。教师须提前确认 MCP 可用及所需权限。
2. **初始化及分支**：默认主分支为 `main`。允许通过 MCP 或平台初始化空仓库所必需的 README 等初始记录；业务代码、测试、原型、约束、Skill、配置及后续文档变更均在 `dev/<题号>` 开发分支提交和推送，不得直接提交或推送到 `main`。预先初始化不算完成任何业务开发阶段。
3. **全程在开发分支推进**：按需求、原型、计划、开发、测试、验收等阶段保留真实提交；不能开发结束后一次性补造过程记录。每次提交遵守第 9 节格式和编号核验。
4. **测试通过才申请合并**：功能测试、单元测试、覆盖率、相关并发或竞争检测及 Agent 验收均通过后，从开发分支向 `main` 发起 PR，附需求与缺陷编号、变更说明、实际测试结果、覆盖率、验收报告及 AI/Skill 记录位置。不得将“提交到主分支”理解为直接在主分支写代码。
5. **PR 门禁**：主分支配置禁止直接推送及删除、禁止强推，要求通过 PR 合并并通过规定的状态检查。GitHub 套餐及仓库权限须支持实际配置；规则设置截图或读取结果应随作业提交，不能仅口头声明。
6. **合并与版本变化**：PR 所在版本通过检查才可合并；处理冲突、补修复或主分支更新引入变化时，重新检查最终待合并内容。合并后必须保留开发分支原始提交与 PR 的可追溯关系，优先采用保留原始提交的合并方式。若平台生成合并提交，消息同样按规范关联本次主要工作项，不得修改或抹去原提交对应关系。不得用混合类型的压缩提交掩盖开发历史。
7. **合并后自动部署**：针对主分支实际合并版本重新执行质量门禁、构建和部署，记录部署提交、流水线及制品。不得把开发分支旧版本的成功报告当作主分支已验证或已上线的证据。
8. **失败修复**：合并前失败在开发分支修正并重新检查；合并后发现问题也应在开发分支修正、重新发起 PR，不直接改主分支。需要回退时记录实际操作及结果，不抹除原始历史。
9. **可审计交付**：仓库中保留题号、对应需求与 Bug 工作项、分支、提交、PR、验收及部署的索引。任何密钥、访问令牌及敏感数据不得进入仓库或视频。

### 9. Git 提交规范与工作项校验

执行依据：教师提供的 [commit-convention.md](commit-convention.md)。随题集附同名来源副本，原文不作改写；以下为需直接执行的要求摘要。该规范优先于工具自带的 Conventional Commits 模板和个人默认提交习惯。

提交消息格式：

```text
[类型] [版本号] [需求/Bug编号] 中文描述
```

| 类型 | 用途 | 版本号 | 工作项编号 |
| --- | --- | --- | --- |
| `feat` | 新增功能需求 | 必填 | 必填，真实需求编号 |
| `fix` | 修复已登记飞书 Bug 的问题 | 必填 | 必填，真实 Bug 编号 |
| `hotfix` | 线上紧急修复 | 必填 | 可事后补编号，需保留补录记录 |
| `opt` | 性能、代码质量、重构等优化 | 必填 | 可选 |
| `docs` | 文档变更 | 可选 | 可选 |
| `test` | 测试相关 | 可选 | 可选 |

版本号格式为 `v主版本.次版本.修订号`，编号为飞书项目真实工作项 ID，格式 `#数字`。描述使用简洁中文；一次 commit 只包含一种类型，混合变更须拆分提交。不得因为缺编号将功能变更伪装成 `docs`、`test` 或 `opt`。

在 `feat`、`fix` 提交前，须由 AI 调用 meegle CLI 核验对应编号，并保留实际输出：

```bash
meegle workitem get --work-item-id <数字编号> --project-key r17te9
```

编号必须属于相应需求或缺陷，不能只验证“有这个数字”而关联无关工作项。教师开考前应确保本项目与权限可用；不得默认改用其他项目。

原规范规定编号不存在或查询失败时提醒开发者确认。为使教学验收可核查，本题进一步要求：未完成确认和有效核验前不得将该次提交视为合规；不得伪造编号或声称查询成功。普通缺陷须先登记 Bug；`hotfix` 仅适用于真实线上紧急修复，不用于跳过日常编号要求。

## 题目 01：小型电商的订单交易、发货与售前退款

**岗位来源**：[北京易博中天｜Golang（短期1-3个月）](https://www.zhipin.com/job_detail/6b26f6188dd734450nx839q-GVNU.html)。CSV 职责摘录：“参与商品、订单、支付、促销、退款和履约相关服务的开发与优化”“保障交易和状态同步稳定”。

### 业务背景与现场情境

一家 Shop 商城销售少量标准商品，运营负责维护商品售价和可售数量，买家通过网页下单并在线支付，仓库人员根据已付款订单发货，客服处理取消、退款和支付异常。业务虽然规模小，但一个订单同时影响库存、收款、发货和客服处理，单独显示“支付成功”不能说明订单已经正确完成。

本次活动中，某商品只剩 5 件。多名买家同时下单，其中一人迟迟不付款，一人在付款后、仓库发货前要求退款。支付渠道因网络重试重复发送成功通知，另有一笔成功通知在订单超时关闭后才到达。仓库还可能在客服处理退款时点击发货。如果系统处理不清，可能出现超卖、重复退款、买家已退款却继续发货，或者渠道已收款但商城查不到有效订单。

你需要交付供买家、仓库、客服共同使用的小型交易系统。买家知道钱和订单去了哪里，仓库知道哪些单可以发，客服知道哪些异常需要处理，运营在活动结束后能核对订单、库存和收退款结果。

### 参与角色与业务起点

- 买家：浏览在售商品、下单、付款、查询、取消及申请售前退款。
- 运营：维护商品上下架，查看可售数量和交易汇总。
- 仓库：查询可发货订单，填写承运方和运单号完成发货登记。
- 客服：审核售前退款、处理迟到支付并记录原因。
- 模拟支付渠道：受理付款、发出支付通知，受理退款并报告退款结果。

预置 2 个商品、3 个买家及上述员工账号；一种商品单价 10000 分、可售数量 5 件。每单仅购买一种商品，数量 1～2 件，使用人民币分，不含运费和优惠。

### 需要完成的业务范围与规则

1. 买家只能购买在售且数量足够的商品。订单保存下单时的商品与价格，后续上下架和价格调整不改变已有订单金额；创建订单后的可售数量须能反映已占用数量。
2. 待付款订单保留 10 分钟。买家主动取消或超时关闭后释放占用，重复关闭不多释放；超时判断采用服务端时间。
3. 有效支付通知须通过鉴权、匹配订单及金额。重复通知不能重复记款；同一渠道交易号不得归属于两个订单。金额不符、未知订单、验签失败须能查询处理结果。
4. 服务端在订单有效期内收到并校验通过的付款通知可使订单进入待发货；超时关闭后收到成功支付通知，不能恢复订单或重新占用库存，应进入异常支付待处理列表，由客服核实后发起退款。
5. 买家对已付款但未发货订单可申请整单退款，申请期间暂停发货。客服可同意或拒绝并写明原因；拒绝后允许继续发货。退款与发货同时发生时，只能形成一种合法业务结果。
6. 退款经模拟渠道确认成功后，买家能看到退款结果，正常售前退款恢复相应可售数量；渠道明确失败时保留待处理记录，由客服重试。迟到支付对应的退款不得再次恢复此前已释放的数量。
7. 仓库只能为合法待发货订单登记一次发货。已发货订单不受理本题售前退款；本题不实现签收、退货及售后物流。
8. 运营可按订单查询收款、退款、发货和异常处理记录，并查看商品可售数量、已收款及已退款汇总。异常记录不能通过直接修改订单状态消失。

### 必须演示的完整工作场景

- 活动正常成交：运营上架 → 买家购买付款 → 仓库发货 → 买家查询运单 → 运营核查收款与库存。
- 缺货与弃单：20 个并发下单请求争抢有限数量 → 部分订单未付款关闭 → 其他买家购买释放的商品。
- 售前退款：买家付款后申请 → 仓库尝试发货受限 → 客服批准 → 首次退款失败、再次成功 → 订单与数量恢复一致。
- 迟到支付：订单先关闭 → 支付成功通知到达 → 客服从异常列表发现 → 发起退款 → 运营确认无重复释放和重复退款。
- 操作竞争：退款申请与发货并发、重复支付和退款通知、越权查看或处理他人订单，均须有明确结果。

### 原型、Skill 与单日边界

原型须覆盖商品与订单页、仓库待发货页、客服退款及异常支付页、运营核查页，可合并到少量标签页。自编业务 Skill 用于检查订单、库存、支付、退款和发货之间的业务约束及跨环节异常；验收 Skill 必须检查上述完整场景。

采用固定商品、模拟支付和人工发货登记；不做购物车、多商户、真实物流、部分退款或完整财务系统。必须执行第一部分全部要求，不能只交支付通知接口。
