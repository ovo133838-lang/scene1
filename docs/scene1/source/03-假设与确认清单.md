| A02 | 用户主动取消后才收到真实付款 | 与超时关闭采用相同异常收款处理：不恢复、不占货，核实退款 | 已确认 U05；同步 R06、AC13 |
| A03 | 商品 B、商品名称和员工数量 | 商品 A“教学商品 A”10000 分/5 件；商品 B“教学商品 B”20000 分/8 件；买家 A/B/C，运营/仓库/客服各 1 个独立账号；教学数据明确标识 | 仅影响演示数据，可在原型前调整；第二商品价格库存不是题目原定值 |
| A04 | 买家网络重试下单、相同编号换参数 | 同买家同下单请求编号及参数返回同一订单；同编号换商品/数量拒绝。同样原则用于退款申请、审核、发货和库存调整，避免重试产生新业务动作；新的独立请求编号才代表新操作 | 有助于区分 20 个合法独立请求与同请求重试；具体字段后续设计，开发前确定 |
| A05 | 同订单出现不同成功交易号、金额不符或未知订单 | 教学付款页对一单只完成一次真实模拟扣款。外部注入的冲突交易仍记录异常；无可信核实不记正常收款、不放行发货。可信核实存在额外款项时计入独立异常收款并由客服处理，不覆盖旧交易 | 防止把金额错误或额外付款当正常交易；异常实际退款需可信交易依据，不增加完整财务系统；开发前明确模拟边界 |
| A06 | 退款审核期间买家撤回申请；客服重复审核 | 本题不提供买家撤回；同一申请只得一个审核结论。审核通过后不能改成拒绝，已驳回不改写，只能新申请 | 控制单日范围；开发前确认此交互边界 |
| A07 | 退款失败后的旧回报与新重试 | 一个已确认收款只创建一个整笔逻辑退款；明确失败方可产生新的可追踪尝试，未知时只查询。旧尝试回报仅在与可信渠道终态一致时影响该退款；冲突回报保留待核实，不使已成功倒退、不多记退款 | 避免“失败→重试→旧成功”导致多退；模拟渠道应保证明确终态并支持状态查询，技术设计时固定协议 |
| A08 | 已下架或已调价后旧订单是否继续付款/发货，退款恢复到哪里 | 旧订单按快照继续履约；退款恢复该商品可售数值，但下架状态不自动上架，仍不能创建新订单 | 已确认 U06；同步 R01、R05、AC03 |
| A09 | 运营调整库存的粒度 | 用正/负调整数量，不任意覆盖总库存；减少量不得超过当前可售，原因必填。重复操作按 A04 去重；保存调整前后数和调整净额 | U01 已确认可调整，本项细化操作以便库存等式可核查；原型前审阅 |
| A10 | 人员身份和教学时钟如何演示 | 使用预置账号的可信认证会话，不接受客户端自报用户 ID 作为身份；默认真实服务端 10 分钟，演示可配置统一教学时钟，但不能仅缩短前端倒计时 | 认证方式、时钟机制属于设计选择，开发前说明；既有安全与同规则要求来自原题 |
| A11 | 查询成功/已确认实收统计口径 | 有效可信成功收款记实收，迟到等异常实收单列但计入实收总额；未核实通知不冒充实收；退款成功才扣减。计量使用人民币整数分，界面可显示元 | 避免“收到通知条数=收款笔数”；原型前审阅统计文案及异常查询范围 |
| A12 | 支付请求超时但渠道尚未有可信终态 | 买家显示付款待确认，不直接变已付款；按原订单截止及有效通知时点裁决。未确认前沿用渠道支付标识查询，避免用户重复实际扣款；超时后才有效成功则走异常收款 | U03 确认的是退款未知，本项是支付未知的分析建议，不能视作已确认；开发前确定 |
